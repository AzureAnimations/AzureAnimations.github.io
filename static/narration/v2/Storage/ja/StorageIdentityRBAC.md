# ナレーション台本 — Azure Storage · レベルアップ · ID と RBAC

**Source animation:** `static/v2/Storage/StorageIdentityRBAC.html`

---

## Step 1 · goal

[confident] アプリはコンテナー内の blob を読み取る必要があります。そして目標は、キーを一切使わずにそれを実現することです。
[600ms]
[calm] 従来のやり方はアカウントキーや SAS トークンを渡します。これは漏えいしうる秘密です。最新のやり方は、代わりにアプリに ID を与え、ロールを付与します。
[700ms]
[curious] その全体像を、矢印を一つずつたどって作りましょう。左側の ID が、右側のコンテナーへのアクセスを獲得していきます。

## Step 2 · identity

[confident] まず、アプリにはセキュリティプリンシパルが必要です。つまり、誰が要求しているのか、ということです。
[600ms]
[calm] それはユーザー、グループ、あるいはサービスプリンシパルかもしれません。しかしアプリにとって最良の選択はマネージド ID です。Azure が資格情報を管理するので、コードの中に秘密はありません。
[700ms]
[reassuring] そして DefaultAzureCredential ヘルパーを使えば、まったく同じコードがあなたのノート PC でも Azure でも動きます。

## Step 3 · token

[confident] さてアプリが Storage を呼び出します。Microsoft Entra ID がその ID を認証し、短命の OAuth トークンを返します。
[600ms]
[calm] Storage は Entra を信頼しているので、そのトークンが — キーではなく — すべての要求に付いて回ります。
[700ms]
[reassuring] トークンはすぐに期限切れになり、storage にスコープされているので、あなたが保存したりローテーションしたりするものは何もありません。

## Step 4 · role

[confident] トークンだけではまだ足りません。ID にはロールが必要です。そしてここに、誰もがつまずく落とし穴があります。
[600ms]
[serious] Storage Blob Data Reader のような、データプレーンのロールを使ってください。コントロールプレーンの共同作成者ロールはアカウントを管理できますが、あなたの blob は読み取れません。
[700ms]
[amused] つまり共同作成者は、リソースを平然と管理しながら、データに対しては 403 を受け取ります。データロールを割り当てましょう。

## Step 5 · scope

[confident] すべてのロールはスコープで割り当てられます。管理グループから、サブスクリプション、リソースグループ、アカウントを経て、単一のコンテナーに至るまで。
[600ms]
[calm] 機能する最も狭いスコープで割り当ててください。ここではコンテナーです。そして権限はそこから下へと継承されます。
[700ms]
[reassuring] blob パスの精度が必要ですか？ 割り当てそのものに、属性ベースの条件、つまり ABAC を追加しましょう。

## Step 6 · assign

[confident] まとめると、ロールの割り当てができあがります。プリンシパルと、ロールと、スコープです。
[600ms]
[calm] これですべての要求が Entra トークンを運び、Azure が割り当てを確認し、アプリが blob を読み取ります。キーは一切関与しません。
[700ms]
[reassuring] ロールの割り当ては要するに、誰が、何を、どこで、です。そして Azure は一回一回の呼び出しごとにそれを評価します。

## Step 7 · recap

[proud] これが全体像です。アプリの ID から、Entra トークンへ、コンテナースコープのデータプレーンロールへ、そして blob へ。
[600ms]
[calm] キーはなく、最小権限で、完全に監査されています。
[700ms]
[encouraging] 最後の一手 — 共有キーをオフにして、ID を唯一の入り口にしましょう。

## Step 8 · spec

[confident] 大事なことなので、もう一段深く。Azure のロールベースアクセス制御には二つのプレーンがあります。
[600ms]
[calm] 所有者や共同作成者のようなコントロールプレーンのロールはリソースを管理します。データプレーンのロール — blob 向けの Reader、Contributor、Owner、そしてファイル、キュー、テーブル向けのその仲間たち — は、中のデータへのアクセスを付与します。
[700ms]
[serious] 覚えておいてください。所有者と共同作成者はアカウントキーを一覧できるので、従来のやり方でデータに到達できてしまいます。共有キーを無効にして、全員を適切なデータロール経由に強制しましょう。
