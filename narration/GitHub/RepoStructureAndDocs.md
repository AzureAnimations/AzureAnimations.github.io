## Step 1 · A Repo With Only Code

[calm] Priya just joined Contoso's weather team, and she opens the weather map repository. The code is all there.
[600ms]
[curious] But nothing tells her what the project is, whether she may use it, how to help, who reviews changes, or where to report a flaw.
[600ms]
[confident] That's the problem, and the fix is simple: add the few files that answer those five questions.

## Step 2 · Five Files Answer Five Questions

[curious] Each question has a home, and it's just a plain file that GitHub knows how to find and show.
[600ms]
[confident] The README says what the project is and how to start. The license says what people may do with it. Contributing explains how to help.
[600ms]
[reassuring] Code owners says who reviews, and the security file says how to report a flaw. Add them, and nobody has to ask.

## Step 3 · Where Each File Lives

[calm] GitHub looks in three places: the root of the repository, a docs folder, and the hidden dot github folder.
[600ms]
[confident] For the README and code owners, it checks the dot github folder first, then the root, then docs, and the first match wins.
[600ms]
[reassuring] Contributing and security files can sit in any of the three. Keep the license in the root.

## Step 4 · Start From a Template, Then Add Files

[curious] A template gives a brand-new repository the same folders and files in one click. You choose Use this template, and you decide whether to include only the default branch or all branches.
[600ms]
[confident] That's different from a fork, which keeps the full history. A template starts fresh with a single commit.
[600ms]
[calm] After that, a new file goes onto a branch, ready for a pull request.

## Step 5 · Read the Repo’s Dashboard

[calm] The Insights tab turns activity into charts. Pulse, contributors, traffic and commits show how busy the repository is and who's using it.
[600ms]
[confident] Community standards is a checklist of the recommended health files, so you can see what's still missing.
[600ms]
[impressed] And the dependency graph lists what the repository uses, what uses it, and any known vulnerabilities.

## Step 6 · Issue, Pull Request or Discussion?

[curious] There are three places to talk, and each has a different job. Pick by what you need.
[600ms]
[confident] An issue tracks work, like a bug, a task or an idea. A pull request proposes a change and gets it reviewed and merged.
[600ms]
[reassuring] A discussion is open-ended: questions, ideas, announcements and polls. If an issue turns into a conversation, you can convert it into a discussion.

## Step 7 · Link the Fix to the Issue

[calm] Here's a small habit that saves a lot of tidying. Put a closing keyword in the pull request description, like fixes or closes, followed by the issue number.
[600ms]
[confident] When that pull request is merged into the default branch, GitHub closes the issue for you. Merged anywhere else, and the keyword is ignored.
[600ms]
[reassuring] For an issue in another repository, add the owner and repository name. You can also link by hand from the sidebar.

## Step 8 · Templates, Assignments and Filters

[calm] A busy repository needs three small tools, and the first is a template, which makes issues arrive complete.
[600ms]
[confident] Issue templates and forms live in the dot github issue template folder, and a pull request template pre-fills the description. Assignees show who owns the work.
[600ms]
[impressed] Then filters narrow the list. A query like is open, label bug, assignee me finds exactly what you need.

## Step 9 · Watch What Matters

[curious] You choose how closely you follow a repository: just participating and mentions, all activity, custom, or ignore.
[600ms]
[confident] Comment on a conversation or get mentioned, and you're subscribed automatically. Everything lands in one inbox.
[600ms]
[reassuring] There you can mark items done, save them for later, or unsubscribe. Unsaved notifications are kept for three months.

## Step 10 · Gist, Wiki or Pages?

[curious] Not everything belongs in the README. Pick the home by the job.
[600ms]
[confident] A gist is a snippet that's itself a Git repository, public or secret, and secret doesn't mean private. A wiki holds long-form notes beside the code.
[600ms]
[calm] Pages publishes a static website from a repository, and search engines can index it.

## Step 11 · Three More Helpers for Managing Work

[calm] A few small tools sit around the project board. Milestones group issues and pull requests, and show percent complete and a due date.
[600ms]
[confident] Saved replies are reusable responses tied to your account, handy in issues, pull requests and discussions.
[600ms]
[curious] Project insights chart the items in a project, now and over time. The board itself comes in the next lesson.

## Step 12 · A Healthy Repo, a Working Team

[calm] The right files inside, and the right tools around. That's what a repository that's easy to work in looks like.
[600ms]
[confident] Keep the community checklist green, route reviews with code owners, triage with templates and filters, and keep each conversation where it belongs.
[600ms]
[proud] Next, you'll plan the work on a Projects board.
