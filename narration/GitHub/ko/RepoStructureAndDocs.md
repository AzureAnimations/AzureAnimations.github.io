## Step 1 · A Repo With Only Code

[calm] Priya는 Contoso의 기상 팀에 막 합류했고, 기상 지도 저장소를 엽니다. 코드는 모두 거기에 있습니다.
[600ms]
[curious] 하지만 프로젝트가 무엇인지, 사용할 수 있는지, 어떻게 도울 수 있는지, 누가 변경 사항을 검토할지, 결함을 어디에 신고해야 하는지 알려주는 것은 아무것도 없습니다.
[600ms]
[confident] 그게 문제이며, 해결책은 간단합니다: 그 다섯 가지 질문에 답하는 몇 개의 파일을 추가하는 것입니다.

## Step 2 · Five Files Answer Five Questions

[curious] 각 질문에는 집이 있고, GitHub 찾는 법을 알고 보여주는 평범한 파일일 뿐입니다.
[600ms]
[confident] README에는 프로젝트가 무엇인지, 어떻게 시작해야 하는지 명시되어 있습니다. 라이선스는 사람들이 무엇을 할 수 있는지를 명시합니다. 기여는 어떻게 도울 수 있는지 설명합니다.
[600ms]
[reassuring] 코드 소유자는 누가 검토하는지 결정하고, 보안 파일에는 결함을 어떻게 보고할지 나옵니다. 그들을 추가하면 아무도 묻지 않아도 됩니다.

## Step 3 · Where Each File Lives

[calm] GitHub 세 곳을 찾습니다: 저장소의 루트, 문서 폴더, 그리고 숨겨진 닷 깃허브 폴더입니다.
[600ms]
[confident] README와 코드 소유자는 먼저 dot github 폴더를 확인하고, 그 다음 root, docs를 확인하며, 첫 번째 매치가 승리합니다.
[600ms]
[reassuring] 기여 파일과 보안 파일은 세 가지 중 어느 곳에 저장할 수 있습니다. 라이선스는 루트에 유지하세요.

## Step 4 · Start From a Template, Then Add Files

[curious] 템플릿은 새 저장소에 동일한 폴더와 파일을 한 번의 클릭으로 제공합니다. 이 템플릿을 선택하고, 기본 브랜치만 포함할지 모든 브랜치만 포함할지 결정합니다.
[600ms]
[confident] 이것은 전체 기록을 유지하는 포크와는 다릅니다. 포크는 전체 기록을 유지합니다. 템플릿은 단일 커밋으로 새로 시작합니다.
[600ms]
[calm] 그 다음에는 새 파일이 브랜치에 올라가 풀 리퀘스트를 준비합니다.

## Step 5 · Read the Repo’s Dashboard

[calm] 인사이트 탭은 활동을 차트로 변환합니다. 펄스, 기여자, 트래픽, 커밋 수는 저장소가 얼마나 붐비고 누가 사용 중인지를 보여줍니다.
[600ms]
[confident] 커뮤니티 스탠다드는 추천된 건강 파일 체크리스트로, 아직 빠진 부분을 확인할 수 있습니다.
[600ms]
[impressed] 그리고 의존성 그래프는 저장소가 사용하는 것, 사용하는 것, 그리고 알려진 취약점을 나열합니다.

## Step 6 · Issue, Pull Request or Discussion?

[curious] 대화할 수 있는 곳이 세 곳 있고, 각각 다른 직업이 있습니다. 필요한 것을 골라보세요.
[600ms]
[confident] 이슈는 버그, 작업, 아이디어 같은 작업을 추적합니다. 풀 리퀘스트는 변경을 제안하고, 검토를 거쳐 병합됩니다.
[600ms]
[reassuring] 토론은 질문, 아이디어, 공지, 설문조사로 열린 끝이 있습니다. 어떤 이슈가 대화로 번지면 토론으로 전환할 수 있습니다.

## Step 7 · Link the Fix to the Issue

[calm] 정리를 많이 덜어주는 작은 습관이 있습니다. 풀 리퀘스트 설명에 수정이나 마감 같은 마감 키워드를 넣고, 그 뒤에 문제 번호를 적으세요.
[600ms]
[confident] 그 풀 요청이 기본 브랜치에 병합되면, GitHub 문제가 자동으로 종료됩니다. 다른 곳에 병합하면 키워드가 무시됩니다.
[600ms]
[reassuring] 다른 저장소의 문제가 발생하면 소유자와 저장소 이름을 추가하세요. 사이드바에서 직접 링크할 수도 있습니다.

## Step 8 · Templates, Assignments and Filters

[calm] 바쁜 저장소에는 세 가지 작은 도구가 필요하며, 첫 번째는 템플릿으로, 이슈가 완성되어 있습니다.
[600ms]
[confident] 이슈 템플릿과 폼은 dot github issue 템플릿 폴더에 저장되어 있고, 풀 리퀘스트 템플릿이 설명을 미리 채워줍니다. 할당인은 작업 소유자를 보여줍니다.
[600ms]
[impressed] 그 다음 필터로 목록을 좁혀줍니다. 쿼리는 열려 있고, 라벨 버그, assignee me와 같은 것들이 정확히 필요한 것을 찾아줍니다.

## Step 9 · Watch What Matters

[curious] 저장소를 얼마나 밀접하게 따라갈지 선택할 수 있습니다: 참여와 언급만 하거나, 모든 활동, 커스텀, 또는 무시할 수도 있습니다.
[600ms]
[confident] 대화에 댓글을 달거나 언급되면 자동으로 구독됩니다. 모든 것이 한 편지함에 모입니다.
[600ms]
[reassuring] 거기서 완료 항목을 표시하거나, 나중을 위해 저장하거나, 구독을 취소할 수 있습니다. 저장하지 않은 알림은 3개월간 보관됩니다.

## Step 10 · Gist, Wiki or Pages?

[curious] 모든 것이 README에 속하는 것은 아닙니다. 일자리별로 집을 선택하세요.
[600ms]
[confident] 기스트는 그 자체로 Git 저장소인 스니펫이며, 공개적이든 비밀이든, 비밀이 비공개를 의미하지는 않습니다. 위키는 코드 옆에 긴 형태의 메모를 보관합니다.
[600ms]
[calm] Pages는 저장소에서 정적인 웹사이트를 게시하며, 검색 엔진이 이를 인덱싱할 수 있습니다.

## Step 11 · Three More Helpers for Managing Work

[calm] 프로젝트 보드에는 몇 가지 작은 도구들이 있습니다. 마일스톤은 이슈와 풀 요청을 그룹화하고, 완료 비율과 마감일을 표시합니다.
[600ms]
[confident] 저장된 답변은 계정에 연동된 재사용 가능한 답변으로, 이슈, 풀 리퀘스트, 토론 시 유용합니다.
[600ms]
[curious] 프로젝트 인사이트는 현재 프로젝트와 시간이 지남에 따라 프로젝트 내 항목을 도표화합니다. 보드 자체는 다음 수업에서 나옵니다.

## Step 12 · A Healthy Repo, a Working Team

[calm] 적절한 파일과 주변에 적절한 도구들이 있어야 합니다. 이것이 바로 작업하기 쉬운 저장소의 모습입니다.
[600ms]
[confident] 커뮤니티 체크리스트를 항상 잘 관리하고, 코드 소유자와 검토를 라우팅하며, 템플릿과 필터로 분류하고, 각 대화를 제자리에 두세요.
[600ms]
[proud] 다음으로, 프로젝트 보드에서 작업을 계획하게 됩니다.
