## Step 1 · Nobody Pushes Straight to main

[confident] ボードはこのカードを In Progress と示しています。コードを書く時間です。そして最初の問いは、どこに置くか。
[500ms]
[serious] main ではありません。main はデプロイされるものだから、唯一、誰も直接書き込まないブランチです。Contoso はそれをルールセットで強制します。プルリクエストを必須に、チェックを必須に、レビューを必須に、強制プッシュを禁止に。
[500ms]
[thoughtful] 人が*同意した*だけの取り決めは、悪い金曜の午後に破られます。ルールセットは破られません。しかもメンテナーにも同じように適用されます。

## Step 2 · Three Tiers, Not Two

[confident] 多くのチームは二段で止まります。main と、変更ごとのブランチ。Contoso はその間にもう一段を置きます。
[500ms]
[calm] main、常にデプロイ可能。その下にエピックブランチ。長命で、エピックごとに一本、そのエピックのサブタスクを統合します。さらにその下にフィーチャーブランチ。短命で、サブタスクごとに一本、閉じるイシューの名前を付けます。
[500ms]
[bright] この中間の段こそが要点です。エピックまるごとを組み上げ、*一つのもの*として検証してから、初めて一部でも本番に届く。

## Step 3 · Clone It — and All You Have Is main

[warm] ここまではすべて GitHub 上の話でした。コードを書くには、手元のマシンに持ってくる必要があります。
[500ms]
[calm] 緑の Code ボタンを押してアドレスをコピーし、`git clone` に貼り付けます。手に入るのはダウンロードではありません。履歴を丸ごと備えた、リポジトリの完全な複製です。
[500ms]
[reassuring] では `git branch` と入力してください。一行だけ。星印と main の文字。作ったばかりのクローンにはブランチが一本しかなく、しかもそれが保護されたほうです。だから次にすることは、自分のブランチを作ることです。

## Step 4 · Cut the Epic Branch, Then the Feature Branch

[confident] コマンドは二連。そして順序が大事です。
[500ms]
[calm] まずエピックブランチ。main をチェックアウトし、プルして、デプロイ済みの状態から始めるようにし、作成して、チームから見えるようにプッシュします。
[500ms]
[bright] 次にフィーチャーブランチ。自分がどこに立っているかに注目してください。あなたはエピックブランチの*上*にいて、そこからフィーチャーブランチを切ります。
[500ms]
[serious] 切る場所を間違えると、プルリクエストが他人のコミットで埋まり、レビューが読めなくなります。

## Step 5 · A Commit Is a Set of Changes

[confident] では、コミットとは本当は何なのか。一ファイルのことのように言う人がいますが、違います。
[500ms]
[calm] サブタスク 一 点 一 はバックエンドです。サーバー、ヘルスのルート、都市のルート、Azure Maps のサービス、パッケージファイル、環境変数の見本ファイル、そして README の修正。
[500ms]
[bright] 七ファイル。新規が六、変更が一。七つすべてが一緒に、*一つの*コミットとして入ります。
[500ms]
[serious] そこで、混同されがちな三つのコマンドを。三つの別々の場所で起きるからです。`git add` は何も保存しません。選ぶだけです。`git commit` は選んだものを、自分のマシン上の履歴に書き込みます。そして `git push` だけが GitHub に触れます。

## Step 6 · Write the Issue Number Into the Commit

[confident] 作業は終わり、コミットメッセージが要ります。
[500ms]
[calm] `feat` がどんな種類の変更かを示し、続いて素直な説明。そして末尾にかっこでイシュー番号。この参照が線を引き戻します。コミットがイシュー 二 に現れるようになります。
[500ms]
[thoughtful] 半年後、この行がなぜ変わったのかを覚えている同僚は `git log` だけです。それに答えさせるものが、このイシュー番号です。

## Step 7 · One Number, Three Places

[thoughtful] ではなぜメッセージの末尾がシャープ 二 なのか。GitHub がそれを読むからです。
[500ms]
[calm] コミットがプッシュされた瞬間、GitHub がイシュー 二 に一行を加えます。このイシューを参照したコミットがある、と。イシューを開けばそれに答えたコードが見え、コミットを開けばそれを求めたタスクが見えます。半年後、この行の blame 注釈にも、まだその番号が載っています。
[500ms]
[careful] 注意が一つ。裸のシャープ 二 は*リンクするだけ*です。実際にイシューを閉じるにはキーワードが要ります。closes シャープ 二。次のプルリクエストがそれを持ちます。

## Step 8 · Open the Pull Request Into the Epic

[confident] プルリクエストを開きます。そして、ここが皆の間違えるところです。
[500ms]
[serious] ベースブランチはエピックブランチです。main ではありません。すべてのサブタスクは、まず自分のエピックに着地します。
[500ms]
[bright] 本文には二語と数字。Closes シャープ 二。これがマージされると、イシューが自分で閉じ、エピックのタスクリストのチェックが入り、カードが Done に移ります。三つのことが、一行の文字から。

## Step 9 · The Checks Decide, Not the Author

[confident] プルリクエストを開くと、パイプラインが動き出します。
[600ms]
[calm] プロジェクトがビルドされる。単体テストが走る。CodeQL がコードのセキュリティ問題を調べる。そしてチームメイトが読む。
[600ms]
[serious] そのすべてが緑になるまで、マージボタンは無効のままです。全員に対して。書いた本人に対しても。
[600ms]
[reassuring] だからステップ 一 のルールセットが効いてくるのです。なければこれらのチェックはただの助言。あれば、関門になります。

## Step 10 · When the Epic Is Whole, Promote It

[confident] サブタスク 二 がマージされる。サブタスク 三 がマージされる。エピックブランチは今、完成し統合されたバックエンドを持ち、断片としてではなく一つの単位として検証されています。
[600ms]
[calm] そこで最後のプルリクエストが `epic/backend-api` を main へ運びます。
[600ms]
[bright] そして*それ*が、出荷するマージです。それ以前はすべて統合でした。これがデプロイのワークフローを起動します。

## Step 11 · Epic 1, From Cut to Merge

[warm] 直前の五ステップを一枚の絵にして、エピック 一 だけを追いましょう。
[500ms]
[calm] いちばん上に main。コミットが一つ、あとは何もなし。物語のあいだ、じっと止まっています。その下、main から切られたエピックブランチ。最初は空です。作業場ではなく、入れ物だからです。
[500ms]
[calm] サブタスク 二 がエピックから短いブランチを一本もらいます。コミットが一つ。プルリクエスト十三番が戻し、本文に「Closes #2」とあったので、イシューは自分で閉じます。
[500ms]
[bright] 続いてサブタスク 三 も同じことをします。自分のブランチ、自分のコミット、プルリクエスト十四番。Copilot のエージェントが開いた、あのプルリクエストです。
[500ms]
[confident] 真ん中の車線を数えてください。コミットは二つ、サブタスクごとに一つ。そして今になって、エピックが完成して初めて、プルリクエスト十五番がそれを main へ運びます。

## Step 12 · How It Actually Played Out

[confident] では引いて見ましょう。エピック 一 は四つのうちの一つで、どれも同じ形をしています。
[500ms]
[calm] バックエンド API。フロントエンド。テストとパイプライン。セキュリティとデプロイ。それぞれ main から切られ、それぞれ自分のサブタスクで満たされ、それぞれちょうど一本のレビュー済みプルリクエストで戻ってきます。十五、十八、二十一、二十四。
[500ms]
[thoughtful] フィーチャーブランチが消えたわけではありません。この車線の*中*に生きています。この図は、main に届いたマージまで引いて見たものです。
[500ms]
[calm] 順序に注目してください。それぞれのエピックが完成して昇格してから、次が始まります。main は常に、まるごと検証された塊としてのみ前に進みます。
[500ms]
[reassuring] 例外が一つ。いちばん最初のコミットだけが main に直接着地しています。ルールセットを有効にする前のことです。

## Step 13 · One Issue, One Branch, One Safe Merge

[warm] これがモデルの全体です。
[500ms]
[calm] ルールセットで守られた main。エピックごとに一本、その部品を統合するエピックブランチ。イシューごとに一本、その番号を名に持つ短いフィーチャーブランチ。そして、それらが通れるかを決めるチェックの一式。
[500ms]
[confident] すべてはあの緑のチェックに乗っています。では次は、そのパイプラインが実際に何を走らせているのか。
