## Step 1 · What You Have, and What Is Missing

[confident] 何かを足す前に、いま自分がどこにいるかを見ましょう。
[500ms]
[calm] main からブランチを切りました。毎回イシュー番号を書いてコミットしました。プルリクエストを開き、レビュアーが承認しました。この地図の停留所 一、二、三、そして 五 です。
[500ms]
[thoughtful] でも停留所 四 を見てください。すき間があります。ここまで、コードがまだ動くことを実際に*検証した*ものが何もありません。
[500ms]
[serious] レビュアーは変更を読みます。レビュアーはテストスイートを走らせません。三階層下にある脆弱な依存関係にも気づきません。
[500ms]
[bright] だからこのページでは、プルリクエスト自体に自動の関門を足します。緑なら先へ。赤なら修正へ戻る。
[500ms]
[reassuring] 置き場所に注目してください。マージの*前*です。変更がひとたび main に着地すれば全員がそれを取り込み、小さなバグ一つが全員の午後になります。

## Step 2 · The Later You Find It, the More It Costs

[confident] バグを一つ取り上げます。あるいは脆弱性を一つ。振る舞いは同じです。
[500ms]
[bright] 自分のノートパソコンで捕まえれば、費用はほぼゼロ。プルリクエストで捕まえれば、レビュー一巡分。マージ後に捕まえれば、他人の作業からほどく作業になります。本番で捕まえれば、費用は別の次元に入ります。
[500ms]
[thoughtful] だからシフトレフト。そして正確に言えば、「もっとテストする」ではなく、もっと*早く*テストする。これはセキュリティにも、正しさとまったく同じだけ当てはまります。

## Step 3 · What the Pipeline Does — and Why You Want One

[confident] では、その関門では何が走るのか。四つのステージが、決まった順番で。
[400ms]
[calm] Source、プッシュかプルリクエストが実行を始めます。Build、依存関係を復元し、本番と同じやり方でアプリをビルドします。Test、単体テストが走ります。そして Scan、CodeQL がコードを読み、Dependabot がパッケージを調べます。
[500ms]
[bright] Deploy は末尾に破線で置かれています。あれは次のページのもの。ここのすべては、マージの*前*に起きます。
[500ms]
[serious] 四つとも手作業でできるのに、なぜわざわざ。人は金曜には四つ目を忘れるからです。そして人は、今回だけは飛ばそう、と決められてしまうからです。
[500ms]
[reassuring] ワークフローファイルはどちらもしません。毎回、同じ手順。そしてブランチ保護が、緑が返るまでマージを止めます。
[500ms]
[thoughtful] 最後に一つ。Build も Test も Scan も、実際のコンピューターが要ります。では、誰がそれを用意するのか。

## Step 4 · The Machine That Actually Runs It

[confident] ランナーです。ランナーとは単に、あなたのジョブが実行されるマシンのこと。
[500ms]
[calm] たいていは GitHub に用意してもらいます。ubuntu、windows、macos のどれかを頼めば、そのジョブ専用のまっさらな仮想マシンが手に入ります。そのために作られ、終われば破棄されます。
[500ms]
[thoughtful] だから「自分のノートパソコンでは動く」と「CI では通る」は別の主張です。あなたのノートパソコンには何年分もの履歴があり、ランナーには何もありません。
[500ms]
[calm] 料金は分単位。Linux がいちばん安く、Windows はその二倍弱、macOS の一分は Linux のおよそ十倍。公開リポジトリでは無料です。
[500ms]
[serious] GPU が要る、あるいは自社ネットワークへの経路が要る。ならランナーを自前で持つ。分単位の請求はありませんが、パッチも、防御も、前のジョブが残したものの後始末も、自分でやることになります。

## Step 5 · What a Pipeline Actually Is

[confident] パイプラインとは、ドット github スラッシュ workflows の下にある YAML ファイルにすぎません。定義するのは三つです。
[500ms]
[bright] トリガー、いつ走るか。プッシュ、プルリクエスト、スケジュール。ランナー、どこで走るか。そしてジョブ、何を走らせるか。順番に並んだステップ。チェックアウト、Node の準備、インストール、テスト。一つ失敗すればジョブは止まります。
[500ms]
[thoughtful] そして混同されがちな二文字。CI は変更が良いことを証明します。CD は証明された変更を出荷します。同じパイプラインの、続きです。

## Step 6 · Tests That Run Themselves

[confident] では最初のチェック。CI ワークフローがすべてのプッシュとプルリクエストで走ります。依存関係を入れ、テストを走らせる。
[500ms]
[bright] バックエンドでは、天気の応答が正しく解釈されること、そして提供元が落ちたときにどうなるか。フロントエンドでは、都市カードが描画されること、クリックで遷移すること。
[500ms]
[serious] 提供元が落ちたときのテストは、値打ちがあります。Azure Maps はいつか*必ず*使えなくなります。そのときアプリがどう振る舞うかを、Contoso はすでに知っている必要があるのです。

## Step 7 · Let GitHub Read the Code for You

[confident] テストは、コードが期待どおりに動くことを示します。安全であることは示せません。
[500ms]
[calm] そこで二つ目のワークフローが CodeQL を走らせます。すべてのプルリクエストで、そして週に一度も。探すのは、インジェクションと安全でない入力経路、うっかり commit された機密、そして提供元への呼び出しに流れ込む危険なデータの流れ。
[500ms]
[thoughtful] 見つかったものは、人が読む前にプルリクエスト上で提起されます。左に寄せられたセキュリティ。変更がまだ提案の段階のうちに、スキャンが行われます。

## Step 8 · Keep the Dependencies Honest

[confident] 三つ目のチェック。脆弱性の多くは、チームが書いたコードから来るのではありません。パッケージから来ます。
[500ms]
[calm] そこで Dependabot がマニフェストを見張り、上げるべきものがあるたびにプルリクエストを開きます。
[500ms]
[bright] その形に注目してください。更新が*プルリクエストとして*届くので、人間の変更と同じテスト、同じスキャンを通ります。何一つ関門を素通りしません。セキュリティ修正でさえも。

## Step 9 · Where Secrets Are Allowed to Live

[serious] パイプラインに必要でありながら、決してリポジトリに置いてはならないものが一つ。資格情報です。
[500ms]
[calm] Azure Maps のキーは駄目。クライアントシークレットも駄目。今回だけ、と commit したドット env ファイルも駄目です。その「今回だけ」こそが、履歴に永遠に残る道筋だからです。
[500ms]
[confident] それらは Actions シークレットに入ります。暗号化され、書き込み専用。一度保存したら読み出せず、差し替えるだけ。ステップが表示しようとすれば、GitHub が伏せ字にします。
[500ms]
[thoughtful] いちばん最初の解説にあった規則、Azure Maps のキーはサーバー側にとどめる、それをパイプラインに適用したのがこれです。

## Step 10 · Every Change Arrives Already Proven

[warm] これで左半分は完成です。
[600ms]
[calm] チェックは行けるところまで左に寄りました。テストも、セキュリティ解析も、依存関係の更新も、すべてプルリクエスト上で、まっさらなランナーの上で、コードに一度も触れないシークレットとともに走ります。
[600ms]
[confident] 継続的インテグレーションは、これで完了。次は継続的デリバリー。この変更を梱包して、安全に Azure へ届けます。
