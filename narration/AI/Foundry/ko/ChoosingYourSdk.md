# AI SDK 선택하기 — 내레이션

Source animation: `journeys/AI/Foundry/ChoosingYourSdk.html`

한 단계당 한 블록으로 `STEPS[]`와 1:1로 대응합니다. `[NNNms]`는 멈춤입니다.

## Step 1 · 세 개의 SDK, 하나의 애플리케이션

Azure OpenAI SDK. Foundry SDK. Microsoft Agent Framework.
[500ms]
모델을 호출하고 답을 받는, 모두 같은 일을 하는 것처럼 보이는 세 가지 이름입니다.
[600ms]
서로 경쟁하는 관계가 아닙니다. 하나의 스택을 이루는 세 개의 계층이고, 실제 애플리케이션은 대부분 둘 이상을 함께 씁니다.
[400ms]
그래서 질문은 "무엇이 가장 좋은가"가 아닙니다. "내가 필요한 기능이 어느 엔드포인트 뒤에 있는가"입니다.

---

## Step 2 · 하나의 리소스, 두 개의 엔드포인트

모든 것이 이 그림에서 출발합니다.
[500ms]
Foundry 리소스는 서로 다른 두 엔드포인트를 노출합니다. 에이전트, 도구, 평가, 연결을 제공하는 프로젝트 엔드포인트. 그리고 모델을 직접 제공하는 Azure OpenAI 엔드포인트입니다.
[600ms]
OpenAI SDK는 두 번째와, Foundry SDK는 첫 번째와 통신합니다. Agent Framework는 어느 쪽과도 직접 통신하지 않고, Foundry SDK에 의존해 그 위에 올라탑니다.
[400ms]
엔드포인트를 먼저 고르세요. SDK는 거기서 따라옵니다.

---

## Step 3 · Azure OpenAI SDK

가장 아래 계층은 Azure 리소스를 가리키는 평범한 OpenAI 클라이언트입니다.
[500ms]
여기에는 Azure 전용 추상화가 없습니다. OpenAI에 직접 작성하는 것과 같은 코드 형태이고, 그래서 이미 OpenAI 코드가 있다면 가장 빠른 길입니다.
[600ms]
최대 호환성, 가장 낮은 지연 시간, 또는 임베딩이 필요할 때 선택하세요. 임베딩은 특히 중요한데, 프로젝트 엔드포인트는 이를 전혀 라우팅하지 않기 때문입니다.
[400ms]
얻지 못하는 것. 에이전트, 평가, 연결. 이 엔드포인트에는 그중 어느 것도 없습니다.

---

## Step 4 · Foundry SDK

한 계층 위, Foundry SDK는 단일 엔드포인트를 통해 모든 프로젝트 API를 감싸는 얇은 클라이언트입니다.
[500ms]
두 개의 클라이언트를 제공하고, 대부분의 애플리케이션은 둘 다 사용합니다. 연결, 배포, 추적처럼 Foundry 고유 작업을 위한 프로젝트 클라이언트. 그리고 응답, 에이전트, 평가, 미세 조정처럼 OpenAI 형태인 모든 것을 위한 OpenAI 호환 클라이언트입니다.
[600ms]
플랫폼 도구가 등장하는 계층이 바로 여기입니다. 파일 검색, 코드 인터프리터, 웹 검색, 메모리, MCP 서버.
[400ms]
하나의 엔드포인트, 하나의 자격 증명으로 프로젝트 전체를.

---

## Step 5 · Microsoft Agent Framework

가장 위 계층은 모델 클라이언트를 에이전트로, 여러 에이전트를 워크플로로 바꿉니다.
[500ms]
오픈 소스이고 .NET과 Python에서 동작하며 Semantic Kernel과 AutoGen의 후속입니다. 오케스트레이션을 위해 그 둘을 조합하고 있었다면, 여기로 통합하세요.
[600ms]
연결은 FoundryChatClient를 통해 이루어집니다. 즉 아래에서 Foundry SDK에 의존하며, 대안이 아니라 그 위에 얹히는 계층이라는 뜻입니다.
[400ms]
그리고 준비가 되면 같은 코드를 관리형 엔드포인트를 갖춘 Foundry 호스팅 에이전트로 패키징할 수 있습니다.

---

## Step 6 · 서로 어떻게 맞물리는가

같은 세 SDK를 컴포넌트 다이어그램으로 보겠습니다.
[500ms]
애플리케이션은 Agent Framework에 의존합니다. Agent Framework는 Foundry SDK가 제공하는 인터페이스를 필요로 합니다. Foundry SDK는 Foundry 리소스의 프로젝트 API를 필요로 합니다.
[600ms]
그리고 두 번째 경로에 주목하세요. 애플리케이션은 OpenAI SDK에 직접 의존할 수도 있으며, 그 경우 OpenAI v1 인터페이스로 모델에 도달하면서 프로젝트를 완전히 우회합니다.
[400ms]
같은 리소스로 가는 두 경로가 서로 다른 두 역할을 맡습니다.

---

## Step 7 · 실제 애플리케이션에서

이제 배포된 시스템에 놓아 봅시다.
[500ms]
브라우저는 SDK도 비밀 정보도 갖지 않습니다. FastAPI든 ASP.NET이든, 여러분의 서비스가 인증과 속도 제한과 비즈니스 규칙을 담당하며 SDK 클라이언트를 쥐는 유일한 계층입니다.
[600ms]
그 아래에서는 세 SDK가 같은 서비스 안에 공존할 수 있습니다. 모두 같은 Foundry 프로젝트를 가리키고 같은 자격 증명을 받아들이기 때문입니다.
[400ms]
API 키가 아니라 DefaultAzureCredential을 사용하세요. OpenAI 엔드포인트에서는 키도 동작하지만, 프로덕션에서 원하는 것은 관리 ID입니다.

## Step 8 · 그래서 어느 것을 쓰나요?

결정을 표로 정리했습니다. 실제로 쓸 수 있는 형태입니다.
[500ms]
행에서 시작하세요. 해야 할 일을 고르고 오른쪽으로 읽어 나갑니다.
[400ms]
임베딩이나 가장 낮은 지연 시간이라면 OpenAI SDK. Foundry 도구, 평가, 추적, 연결이라면 Foundry SDK. 워크플로 안의 여러 에이전트나 관리형 호스팅 엔드포인트라면 Agent Framework.
[600ms]
체크가 두 개인 행에서는 더 단순한 쪽을 고르세요. 대시는 불가능하다는 뜻이 아닙니다. 엔드포인트가 잘못됐다는 뜻이고, 거기까지 가려면 SDK와 씨름하게 됩니다.

---

## Step 9 · 계층을 고르세요

규칙은 단순합니다. 일을 해낼 수 있는 가장 낮은 계층에서 시작하세요.
[500ms]
모델만 필요한가요. OpenAI SDK에서 멈추세요. 프로젝트의 도구와 평가와 연결이 필요한가요. Foundry SDK로 올라가세요. 여러 에이전트를 조율하나요. 루프는 Agent Framework에 맡기세요.
[600ms]
나중에 한 계층 올라가는 일은 부담이 적습니다. 같은 프로젝트 엔드포인트와 같은 자격 증명이 그대로 이어지기 때문입니다.
[400ms]
동작하는 가장 낮은 계층을 고르세요. 꼭 필요할 때만 올라가세요.
