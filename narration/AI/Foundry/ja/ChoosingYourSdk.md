## Step 1 · Three SDKs, One Application

Azure OpenAI SDK。Foundry SDK。Microsoft Agent Framework。
[500ms]
どれもモデルを呼び出して答えを受け取る、同じことをしているように見える 3 つの名前です。
[600ms]
これらは競合ではありません。1 つのスタックの 3 つの層であり、実際のアプリケーションはたいてい複数を組み合わせて使います。
[400ms]
ですから問いは「どれが一番良いか」ではありません。「必要な機能はどのエンドポイントの向こうにあるのか」です。

## Step 2 · One Resource, Two Endpoints

すべてはこの図から導かれます。
[500ms]
Foundry リソースは 2 つの異なるエンドポイントを公開します。エージェント、ツール、評価、接続を提供するプロジェクト エンドポイント。そしてモデルを直接提供する Azure OpenAI エンドポイントです。
[600ms]
OpenAI SDK は後者と、Foundry SDK は前者と通信します。Agent Framework はどちらとも直接は話さず、Foundry SDK に依存してその上に乗ります。
[400ms]
まずエンドポイントを選ぶ。SDK はそこから決まります。

---

## Step 3 · Azure OpenAI SDK

一番下の層は、Azure リソースに向けた素の OpenAI クライアントです。
[500ms]
ここに Azure 固有の抽象化はありません。OpenAI に直接書くのと同じコードの形なので、既に OpenAI のコードがあるなら最短の道です。
[600ms]
最大の互換性、最小のレイテンシ、または埋め込みが必要なときに使います。埋め込みは特に重要で、プロジェクト エンドポイントはそれをまったくルーティングしません。
[400ms]
得られないもの。エージェント、評価、接続。どれもこのエンドポイントには存在しません。

---

## Step 4 · Foundry SDK

1 つ上の層、Foundry SDK は単一のエンドポイント経由で、あらゆるプロジェクト API を薄くまとめたクライアントです。
[500ms]
2 つのクライアントを提供し、多くのアプリケーションは両方を使います。接続、デプロイ、トレースといった Foundry 固有の操作のためのプロジェクト クライアント。そして応答、エージェント、評価、ファインチューニングなど OpenAI 形式のものを扱う OpenAI 互換クライアントです。
[600ms]
プラットフォームのツールが現れるのはこの層です。ファイル検索、コード インタープリター、Web 検索、メモリ、MCP サーバー。
[400ms]
1 つのエンドポイント、1 つの資格情報で、プロジェクト全体を。

---

## Step 5 · Microsoft Agent Framework

最上層は、モデル クライアントをエージェントに変え、複数のエージェントをワークフローに変えます。
[500ms]
オープン ソースで、.NET と Python で動作し、Semantic Kernel と AutoGen の後継です。オーケストレーションのためにその 2 つを組み合わせていたなら、ここに集約しましょう。
[600ms]
接続は FoundryChatClient を通じて行われます。つまり下層で Foundry SDK に依存しており、代替ではなく上に重なる層だということです。
[400ms]
そして準備ができたら、同じコードをマネージド エンドポイント付きの Foundry ホステッド エージェントとしてパッケージ化できます。

---

## Step 6 · How They Fit Together

同じ 3 つの SDK を、コンポーネント図として見てみましょう。
[500ms]
アプリケーションは Agent Framework に依存します。Agent Framework は Foundry SDK が提供するインターフェイスを必要とします。Foundry SDK は Foundry リソースのプロジェクト API を必要とします。
[600ms]
そしてもう 1 つの経路に注目してください。アプリケーションは OpenAI SDK に直接依存することもでき、その場合は OpenAI v1 インターフェイス経由でモデルに到達し、プロジェクトを完全にバイパスします。
[400ms]
同じリソースへの 2 つの経路が、2 つの異なる役割を担います。

## Step 7 · In a Real Application

これを実際にデプロイしたシステムに置いてみます。
[500ms]
ブラウザーは SDK もシークレットも持ちません。FastAPI でも ASP.NET でも、みなさんのサービスが認証、レート制限、ビジネス ルールを担い、SDK クライアントを持つ唯一の層になります。
[600ms]
その下では、3 つの SDK すべてが同じサービス内で共存できます。すべてが同じ Foundry プロジェクトを指し、同じ資格情報を受け入れるからです。
[400ms]
API キーではなく DefaultAzureCredential を使ってください。OpenAI エンドポイントではキーも動きますが、本番環境で望ましいのはマネージド ID です。

## Step 8 · So Which One Do I Use?

判断はこの表のとおりです。実際に使える形にしてあります。
[500ms]
行から始めてください。やりたいことを選び、右へ読んでいきます。
[400ms]
埋め込み、または最小のレイテンシなら OpenAI SDK。Foundry のツール、評価、トレース、接続なら Foundry SDK。ワークフロー内の複数エージェント、またはマネージドのホステッド エンドポイントなら Agent Framework。
[600ms]
チェックが 2 つ付く行では、シンプルなほうを選びましょう。ダッシュは不可能という意味ではありません。エンドポイントが違うという意味で、そこへ行くには SDK と戦うことになります。

## Step 9 · Pick Your Layer

ルールはシンプルです。仕事をこなせる一番下の層から始めること。
[500ms]
モデルだけですか。OpenAI SDK で止まりましょう。プロジェクトのツール、評価、接続が必要ですか。Foundry SDK へ上がりましょう。複数のエージェントを協調させますか。ループは Agent Framework に任せましょう。
[600ms]
後から 1 つ上の層へ移るのは簡単です。同じプロジェクト エンドポイントと同じ資格情報がそのまま引き継がれるからです。
[400ms]
うまくいく一番下の層を選ぶ。必要に迫られたときだけ登る。
