# Load balancing — ナレーション (ja)

## Step 1 · One name, many servers

[calm] ユーザーが入力するアドレスは一つだけです。その背後には、一つのリージョン、あるいは複数のリージョンに、たくさんのインスタンスが並んでいます。
[500ms]
[confident] どのインスタンスが応答するのかを誰かが決めなければなりませんし、停止しているインスタンスには誰も送らないようにする必要があります。
[400ms]
[curious] そして Azure のロードバランサーは一つではありません。四つあります。選び方を間違えても致命傷になることは多くありませんが、レイテンシーを損ねたり、機能を失ったり、一つのリージョンに単一障害点を抱えたりします。

## Step 2 · Two questions decide it

[confident] マイクロソフトはこれらのサービスを、ちょうど二つの軸で分類しています。
[500ms]
[calm] そのトラフィックはグローバルですか、それともリージョン単位ですか。そして HTTP ですか、それとも任意のプロトコルですか。
[400ms]
[helpful] この順番で答えてください。まずはスコープです。グローバルなサービスをリージョンのサービスの前に置くのは、ごく普通の健全な設計です。逆に、リージョンのサービスにグローバルな役割を演じさせると、すべてのユーザーを一つのリージョンに通すことになります。

## Step 3 · Four services, four quadrants

[calm] 二つの軸を組み合わせると、それぞれのサービスが自分のマスに収まります。
[500ms]
[confident] このグリッドが地図です。このあとの四つのステップで、一マスずつ歩いていきましょう。
[400ms]
[helpful] グリッドが省いている正直な注意点が二つあります。Azure Load Balancer にはリージョン間のフロントエンドもありますし、Application Gateway は HTTP だけでなく TCP と TLS のプロキシもできます。このグリッドは、それぞれが最も推奨される位置を示しています。

## Step 4 · Azure Load Balancer

[confident] Azure Load Balancer は、すべての TCP と UDP のトラフィックを扱うレイヤー四のサービスです。
[500ms]
[calm] 非常に高いスループットと極めて低いレイテンシーのために作られていて、接続を終端せず、パケットをそのまま通します。
[400ms]
[helpful] ここが肝心な点です。クライアントの接続は、バックエンドのサーバー自身に届きます。だからこそレイテンシーがここまで低いのですが、同時に、URL のパスを読めない理由でもあります。

## Step 5 · Contoso, balanced at Layer 4

[calm] 実際のアーキテクチャで見てみましょう。
[500ms]
[confident] パブリックな Load Balancer が一つ、インターネットからのトラフィックを受け取り、その奥の各層の前には内部用の Load Balancer が二つ並びます。ここでのやり取りはすべて TCP です。この図の中に URL を読むものは一つもありません。
[400ms]
[helpful] 数えてみてください。ロードバランサーは一つではなく三つです。パブリックなフロントエンドを持つのは最初の一つだけ。内部の二つはプライベート IP を持つので、ウェブ層の背後にあるものはインターネットからはまったく到達できません。

## Step 6 · Application Gateway

[confident] Application Gateway は、リージョン単位のリバースプロキシです。
[500ms]
[calm] 接続を終端し、HTTP リクエストを読み、URL のパス、あるいはホスト名によって、どこへ送るかを決めます。
[400ms]
[helpful] TLS を終端するため、レイヤー四のバランサーにはできないことができます。リクエストを検査し、WAF を通し、ヘッダーを書き換え、パスごとに別々のプールへ振り分けられるのです。

## Step 7 · One hostname, three back-end pools

[calm] 一つのホスト名が、一つの Application Gateway に解決されます。
[500ms]
[confident] TLS を終端し、リクエストに WAF を通し、そのうえでパスを読んで、サイトの部分ごとに異なる backend pool を選びます。
[400ms]
[helpful] これはレイヤー四のバランサーにはできない芸当です。スラッシュ api とスラッシュ images は、同じアドレスへの同じ接続でやって来ます。それらを分けられるのは、HTTP リクエストを読めるものだけです。

## Step 8 · Traffic Manager

[confident] Traffic Manager は、DNS ベースのトラフィックバランサーです。
[500ms]
[calm] あなたのパケットには一切触れません。名前解決の問い合わせに対して、クライアントが使うべきエンドポイントを答え、そのあとは身を引きます。
[400ms]
[helpful] この設計は強みであり、同時に限界でもあります。DNS に答えるだけなので、どんなプロトコルでも動きます。しかしフェールオーバーは DNS のキャッシュと TTL 次第なので、Front Door ほど速くは切り替えられません。

## Step 9 · One global profile, many regions

[calm] Contoso は同じアプリケーションを複数のリージョンで動かしています。
[500ms]
[confident] Traffic Manager はグローバルです。すべてのリージョンの外側にあって、名前を所有し、問い合わせごとに、そのユーザーを受け持つべきリージョンを返します。
[400ms]
[helpful] 番号を追ってください。ステップ一と二は DNS で、アプリケーションのトラフィックは流れないので破線で描かれています。ステップ三が実際の接続で、これはリージョンへ直接向かいます。Traffic Manager がデータパスに入ることはありません。

## Step 10 · Azure Front Door

[confident] Front Door はアプリケーション配信ネットワークです。
[500ms]
[calm] グローバルなレイヤー七のロードバランシングに加えて、サイトの高速化を、ユーザーの近くにあるマイクロソフトのエッジから提供します。
[400ms]
[helpful] Traffic Manager と違ってリクエストそのものを運ぶので、DNS を待たずに数秒でフェールオーバーでき、キャッシュもできます。アプリケーション全体の世界規模の正面玄関だと考えてください。

## Step 11 · One edge in front of the whole world

[calm] どこにいるユーザーも、最寄りのマイクロソフトのエッジロケーションに届きます。
[500ms]
[confident] Front Door はリクエストを検査し、可能ならキャッシュから応答し、そうでなければ最も健全なオリジンへ転送します。
[400ms]
[helpful] これを Traffic Manager の図と並べてみてください。ここではトラフィックがサービスを実際に通過します。だからこそキャッシュができ、WAF を実行でき、DNS レコードの期限切れを待つのではなく、数秒でユーザーを別のリージョンへ移せるのです。

## Step 12 · They stack, they do not compete

[confident] 現実のアーキテクチャの多くは、これらを複数組み合わせて使います。
[500ms]
[calm] それぞれの層が、下の層にはできない仕事をします。グローバルな到達性、次にリージョン内のレイヤー七のルーティング、そしてマシン間への純粋な振り分けです。
[400ms]
[helpful] 一つの層に四つすべてが必要になることはめったにありません。それでも本格的な公開アプリケーションは、Front Door を Application Gateway の前に置き、その後ろに Load Balancer を置く構成に落ち着くことがよくあります。

## Step 13 · Scope first, then protocol

[confident] では、要点です。
[400ms]
[calm] どこでトラフィックを分散する必要があるのか、そしてサービスはどこまで深く中身を見る必要があるのか。この二つの答えがサービスを決めます。あとはすべて細部です。
[600ms]
[encouraging] 迷ったら、要件を声に出して言ってみてください。「グローバル、ウェブ、キャッシュが必要」なら Front Door。「リージョン、SQL、レイテンシー最優先」なら Load Balancer。その一文が、サービスの名前を教えてくれます。
